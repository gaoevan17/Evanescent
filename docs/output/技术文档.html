1. 项目定位与六场景闭环

1.1 一句话定位

「共识护航」是一个面向合租 / 家庭月末共同开销结算的银行 AI 智能体：用可核对的版本化约定处理共同开销，用证据卡核验异常，用独立授权保护每个人的账户。

主场景自然语言需求：

“帮我们结算本月共同开销，电费按入住天数分，停掉不用的共同会员。妈妈说有一笔陌生扣费，先核实。每个人留够下月开销，再分别安排自己的余钱。”

1.2 三个核心机制

机制 含义 落点
有版本的共识账本 记录费用项目、参与者、分摊方式、权重、有效期、版本及成员确认；规则变更影响后续付款与授权 app/services/ledger.py
证据卡驱动异常核验 关联交易号、商户别名、订阅授权、时间、用户反馈；证据不足保持「待核验」 app/services/evidence.py、bill.py
共同看进度、个人管资金 共享空间仅展示经同意共享的结算状态；余额、完整流水、风险问卷、持仓留在本人私有空间 app/security/policy.py、服务层对象级过滤

跨场景主链：核验共同账单 → 形成并确认分摊规则 → 个人资金预留/必要赎回 → 到账后本人付款 → 回执对账。 异常支线：异常扣费 → 证据核验 → 本人选择订阅或卡片处置。

官网生日预订场景属于参考示例；本项目采用方案二的结算联动场景，不把参考示例当作官方必做项。

5. 权限分级与授权绑定

5.1 权限策略引擎（确定性）

等级 动作 执行前要求
绿色 余额/交易记录/账单分析/理财收益/持仓/产品/风险问卷/本人卡片/共享进度 自动执行
黄色 转账(日累计≤1000元)、订阅查询/取消、虚拟卡申请、AA 收款、证据反馈、提出/确认分摊规则 展示详情 + 明确确认
红色 转账(日累计>1000元)、密码修改、挂失/解挂、理财申购 强验证
红色(团队策略) 赎回、额度调整、交易限制/解锁 强验证

赎回、额度调整、交易限制/解锁官网未逐项明确权限等级，本项目保守按红色处理，并标注为团队策略，不冒充官方要求。

5.2 关键规则

  • 金额统一整数分；执行日按 Asia/Shanghai。
  • 执行前原子校验日累计、并发占用、余额、有效预留、授权有效性。
  • 日累计 1000 元：先转 800 元再转 300 元 → 第二笔日累计 1100 元 → 升级红色。
  • 不能通过拆单、并发或跨会话绕过限额（占用计入当日累计）。
  • 授权绑定：本人身份 + 动作 + 金额 + 收款人/目标资源 + 计划版本 + 规则版本 + 有效期 + 唯一操作标识。
  • 改变关键参数 → 旧授权失效（revoked）；定时任务执行时重新校验；授权过期或风险升级转为等待本人验证。

6. DAG 与状态机

6.1 节点状态机

 pending ──► running ──► success
    │           │
    │           ├──► waiting_confirm ──(确认)──► running
    │           ├──► waiting_auth    ──(验证)──► running
    │           └──► failed / unknown
    │
    ├──► frozen（规则变更冻结，可解冻重规划）
    ├──► skipped（依赖失败）
    └──► cancelled（未执行才可取消）

6.2 计划状态机

 running ──► waiting（存在确认/验证项）──► running ──► completed
    │           │
    ├──► paused ──► running
    ├──► failed / cancelled
    └──► superseded（改口后新计划）

约束：前一步真实状态约束后一步（依赖失败则后序 skipped）；已执行交易只能生成补付/退款等补偿，不能删除流水伪装回滚。

7. 核心算法

7.1 最大余数法分摊（尾差守恒）

quota_i = total * weight_i / Σweight
floor_i = ⌊quota_i⌋
remain  = total - Σfloor_i          # 尾差（0 ≤ remain < 人数）
按「小数余数」降序，前 remain 人各 +1 分

保证 Σamount_i == total（以分为单位守恒）。验收案例：电费 240 元按 30/20/10 → 12000/8000/4000 分；宽带 90 元均分 → 3000/3000/3000 分；合计 150/110/70 元。

7.2 规则变更传播（P-08）

改分摊规则 →
  ① 旧版本 superseded；旧授权 revoked
  ② 冻结受影响的未付款任务（frozen）
  ③ 生成新版本（version+1）
  ④ 按「新分摊 - 已付款」生成补付/退款草稿
  ⑤ 已付款记录保留，未受影响任务继续

7.3 日累计判定

当日已成功+执行中转账总额 already
total = already + 本次金额
total > 100000 分 → 红色；否则 → 黄色

7.4 超时恢复（P-12）

转账请求超时 → 登记系统侧 unknown、银行侧 success → 回读原交易（business_no）→ 银行侧成功则补回执，不重复付款（幂等键兜底）。

9. 安全设计

措施 实现
独立权限校验 app/security/policy.py（确定性，模型/前端/用户文本不可降级）
防编造账户/交易结果 账户信息、交易结果、回执仅来自授权工具回读
防提示注入 商户备注/账单描述/检索结果作为不可信数据，不解析为指令
对象级权限 服务层按身份过滤，同步隔离数据库查询、上下文、日志、导出
完整审计 身份/意图摘要/计划版本/决策理由/证据引用/工具参数/授权引用/认证结果/业务回执/前后状态/时间（不记录验证码、密钥、思维链）

人工接管 接管者仍受本人授权与角色权限约束，无万能管理员

10. 认证实现（强验证）

服务端认证挑战（模拟短信 OTP）实现：过期（默认 300 秒）、一次性消费、防重放（consumed 标记）、限次（默认 5 次）、结果校验（服务端哈希比对）、绑定用户与操作（operation_id 匹配）。

⚠️ 模拟认证说明：本项目的强验证为模拟实现（醒目标记 simulated=true），不等价于正式的人脸/短信/U 盾强验证。模拟资金环境与认证强度是两个独立问题。正式认证及主办方是否接受该方案列为待确认事项，不宣称完全达标。

11. 故障恢复

  • 幂等键：每个业务操作唯一幂等键；超时先按原操作标识查询，不盲目重试。
  • 未执行任务可取消/重规划；已执行交易按业务规则生成补付/退款/补偿。
  • DAG 有状态、持久化，重启后不丢失待处理任务。
  • 转账超时 → 回读银行侧状态恢复回执。
  • 连续失败 → 熔断锁定 + 记录恢复条件。
